# ISOT app review and design audit — Phase 1

**For Amir:** The app already covers the everyday jobs students and venue staff need, and its shared colours and labelled navigation give it a useful foundation. Before polishing Home or packaging it for the App Store, fix several things that could damage members' trust: a member name can run unwanted code when a friend taps Invite, production blocks the scanner's camera, Assembly says votes were recorded without saving them, privacy settings can say “saved” after failure, and Notifications promises alerts it cannot deliver. The running feature needs clearer rules for route records and stronger protection of unfinished and unsaved runs. Some September design concerns have been fixed; others remain. This review proposes changes only. It does not change the app or database.

## Scope and evidence

- Reviewed checkout: `ISOTcommunity/isot-website`, local `website/` directory, commit `82c09eba89f29b03746309bada1d95b5e0753821`, pulled from `origin/main` on 8 October 2026. Working branch: `codex/app-review`.
- Existing local changes to `CLAUDE.md` and untracked transparent logo assets were preserved and excluded from this handover.
- Inventory: all **34 HTML routes**, six first-party files under `app/js/`, shared CSS, service worker, manifest, vendored-library references, deployment configuration, and the calendar/strike API boundaries. Inspected data-to-HTML paths, RPC/table usage, navigation, forms and failure handling. Vendored libraries were not independently audited line by line.
- Ran the repository's `app/check.sh` with the bundled Node runtime: **all 34 pages and seven standalone scripts parse**. This establishes syntax only.
- Rendered all 34 entry routes in headless desktop Chrome at **390 × 844 CSS pixels**, using the real HTML/CSS/JS and an isolated synthetic Supabase replacement. Test identity: “Test Member”, `test@example.invalid`; no real member accounts, names, photos, QR tokens or database writes. `dashboard` and `monitor` redirect to Admin.
- External analytics, backend requests, weather and map tiles were blocked in the browser harness; Font Awesome was allowed. Grey maps in these screenshots are the intentional blocked-tile condition, not proof that live tiles are broken. The service worker was blocked for the layout run. No native or physical-phone test was performed.
- Screenshots: [390px evidence](evidence/390px/). Layout measurements: [measurements.json](evidence/measurements.json). Local reproductions: [probes.json](evidence/probes.json). Empty datasets were intentional; they do not describe production membership or event counts. Missing fields in deliberately minimal Admin/Game fixtures produced `undefined` labels; those are **not recorded as app defects**.
- Checked the public production `/app/scan` response headers: HTTP 200, with `Permissions-Policy: camera=(), microphone=(), geolocation=(self), payment=(), usb=()`. No authenticated production data was accessed.
- Line numbers below refer to the reviewed commit. S = a small local change; M = a coordinated flow/component change; L = backend or multi-flow work. These are relative effort estimates, not deadlines. High = security, privacy, lost data or a core action giving a false result; Medium = broken secondary actions, resilience or accessibility; Low = polish or maintenance. Conditional risks are identified explicitly.

### Phone performance and offline behavior

The app has no framework hydration/bundle overhead and already preloads the topic font. Uploads use shared image shrinking, stripping EXIF by re-encoding; these are good foundations. Observed category art is tens to hundreds of KB rather than a multi-megabyte photo on every page. The 176KB wordmark is larger than needed at a 20px drawer height; use an existing suitable vector/small asset after checking visual fidelity. Do not infer a download problem merely because an unused large image exists on disk.

The external Font Awesome CSS blocks rendering and creates an avoidable dependency for critical control icons. Large dynamic poster images lack reserved dimensions (`home.html:750–761`, `event.html:16,89`), and content inserted above utility tiles can shift them after loading. Prefer an aspect ratio or skeleton space with dimensions informed by the real posters. Maps, tile requests, multi-layer markers and blur effects deserve a mid-range-device trace; no FPS, Core Web Vitals or download-time number is claimed here.

Keep **network-first pages/JS/CSS** as instructed. Supabase and `/api/` responses are excluded from the worker, which avoids caching member payloads. Network-first still means an open TCP connection can delay fallback for a long time; no fetch timeout is defined. First-install shell excludes several key screens, and external CSS/tiles are never cached. Offline auth/profile reads can fail even when HTML is cached; the existing error gate is safer than a fabricated member card. A cached shell is not proof that membership validation or data writes work offline. Shared registration, explicit partial-offline states and durable drafts should be designed together.
